# hvab-blocks — контракт дизайн-системы

Документ для всех, кто пишет токены и блоки этой библиотеки, включая AI-агентов. Это **конституция**: правила, по которым устроены токены, именуются классы и пишутся блоки. Не каталог компонентов и не сборник значений — значения живут в `tokens/`, блоки в `blocks/`.

Основа:

- [Material Design 3 — Design tokens](https://m3.material.io/foundations/design-tokens/overview) — трёхслойная архитектура `ref → sys → comp`.
- [БЭМ](https://ru.bem.info/methodology/) — нейминг селекторов.
- Практика «CSS-переменные как публичный API компонента».

**Цель.** Маленькое каноническое ядро foundation-блоков, где у каждого блока есть токены, понятный публичный API (CSS-переменные), демка и явные правила расширения. Блоки без переписывания встают в **мои контролируемые проекты** и наслаиваются поверх безголовых JS-библиотек. Классы живут в неймспейсе `hb-` (см. §3), поэтому блоки не конфликтуют с глобальными именами проекта-потребителя.

Это не «свой Carbon/Gravity». Это личный verstka-слой: контракт + токены + примитивы и скины + Claude-workflow. **Поведение** сложного интерактива (позиционирование, фокус-трап, клавиатура, тайминги, порталы) не пишем — его даёт потребитель: Radix / React Aria / Floating UI / нативные `<dialog>`/`<details>`. А вот **скины** такого интерактива (tabs, tooltip, popover, modal, sheet, toast и т.п.) — наша работа: блок стилизует структуру классами и реагирует на атрибуты состояний (§4). Полноценная библиотека — побочный продукт нескольких реальных проектов, а не цель сама по себе.

## 0. Стек и принципы

- **Чистый CSS + БЭМ. Без сборки.** Исходники — обычные `.css`-файлы. Никакого SCSS, CSS Modules, PostCSS-only-синтаксиса. Любой потребитель подключает их своим бандлером (Vite, esbuild, Webpack) или прямым `@import`. Если фича требует препроцессора — её нельзя класть в ядро.
- **Framework-agnostic.** Библиотека эмитит только классы и CSS-переменные. Никакого React/Vue API. Разметку и поведение даёт потребитель — вручную или через безголовую либу (Radix, Headless UI, Floating UI, Ark и т.п.).
- **Поведение — снаружи, стиль — внутри.** Блок не содержит JS. Динамические состояния (`open`, `checked`, `disabled`, `loading`) приходят атрибутами от потребителя/headless-либы; блок только реагирует на них стилем (см. §4).
- **Прогрессивность.** Базовый стиль работает на семантическом HTML без единого модификатора. Модификаторы и состояния — добавки, а не обязательное условие.
- **Без сборки → только нативный CSS.** Допустимы CSS custom properties, `@media`, `@supports`. Препроцессорный синтаксис (`@custom-media`/`@custom-selector`) — нет. **CSS Nesting в ядре не используем**, даже нативный: плоские селекторы читаются и переносятся проще, не зависят от форматтеров и пайплайнов потребителя и старых WebView. На маленькой БЭМ-библиотеке вложенность почти ничего не даёт.

## 1. Три слоя токенов

```
ref  →  sys  →  component tokens  →  селекторы блока
                      ↑
        модификаторы и состояния переопределяют
              только component tokens
```

Единый префикс переменных — `--hb-*` для всех слоёв. Слой различается по категории после префикса (`ref`, `color`, `typography`, `<block-name>`).

### 1.1 Reference tokens — `--hb-ref-*`

Сырые значения без семантики: палитра, шкалы радиусов/длительностей. Используются **только** внутри sys-токенов и цветовых схем. Блоки и модификаторы их не трогают.

```css
--hb-ref-palette-blue-500: #3b82f6;
--hb-ref-duration-fast: 150ms;
```

### 1.2 System tokens — `--hb-<category>-*`

Семантический слой. Публичный API темы. Отвечает на «что это», не «какое значение». Блоки используют только этот слой (через component tokens).

| Категория         | Префикс             | Назначение                                                                   |
| ----------------- | ------------------- | ---------------------------------------------------------------------------- |
| Цвет              | `--hb-color-*`      | семантические цвета (см. §5.1)                                               |
| Типографика       | `--hb-typography-*` | size / line / weight / family (см. §9, пилот `text`)                         |
| Радиусы           | `--hb-radius-*`     | шкала скруглений `xs/s/m/l/xl/round`                                         |
| Секционный ритм   | `--hb-spacing-*`    | вертикальные отступы между секциями                                          |
| Компонентный ритм | `--hb-gap-*`        | padding/gap внутри блоков; не смешивать со `spacing`                         |
| Размеры контролов | `--hb-size-*`       | геометрия контролов: `control-height-*`, `control-padding-*`, `border-width` |
| Длительности      | `--hb-duration-*`   | `instant/fast/standard/slow`                                                 |
| Easings           | `--hb-ease-*`       | `linear/out/in/in-out`                                                       |
| Фокус             | `--hb-focus-ring-*` | геометрия фокус-кольца (`width`, `offset`); цвет — `--hb-color-line-focus`   |

Тема (типографика, геометрия, анимации) — одна на проект. Цвет — отдельный слой со схемами (см. §5).

### 1.3 Component tokens — две линии (модель Gravity)

У каждого настраиваемого свойства блока **две переменные**:

- **Публичная** `--hb-<block>-<prop>` — внешний override API. Снаружи (ancestor/инлайн) её ставит потребитель. Сам блок её **не присваивает**, только читает.
- **Приватная** `--_<block>-<prop>` — деталь реализации. В корне блока дефолтится из sys; модификаторы и состояния пишут **в неё**.

Свойство читается как публичная-с-фолбэком-в-приватную:

```css
.hb-button {
  --_button-height: var(--hb-size-control-height-l); /* приватный дефолт из sys */
  height: var(--hb-button-height, var(--_button-height)); /* public ?? private */
}
```

Зачем две линии: модификаторы трогают только приватную, поэтому внешний override публичной (`--hb-button-height`) всегда выигрывает — даже когда применён размерный/вариантный модификатор. Одноуровневая модель этого не давала: модификатор писал бы в ту же переменную, что и внешний override, и побеждал бы его на уровне элемента.

Приватный префикс — `--_<block>-` (с именем блока, чтобы приватные токены вложенных блоков не пересекались через каскад).

## 2. Инварианты слоёв

Жёсткие правила, без исключений:

1. **Блок ссылается только на свои component tokens** внутри селекторов, через двухлинейную форму `var(--hb-<block>-<prop>, var(--_<block>-<prop>))`. Никаких `var(--hb-color-*)` напрямую в `.hb-button__icon`, `.hb-text` и т.п.
2. **Приватные `--_<block>-*` дефолтятся из sys** в корневом селекторе блока.
3. **Модификаторы и состояния пишут только в приватные `--_<block>-*`.** Не в публичные, не в структуру, не добавляют селекторов на внутренние элементы.
4. **Нет «магических» значений с sys-домом.** Всё, у чего есть семантический sys-слой — цвет, типографика, радиусы, размеры контролов, gap/spacing — внутри селекторов блока только через `var(--hb-*)`/`var(--_*)`; не хватает в sys — сначала добавить в sys. Сырые значения этих категорий живут только в `tokens/` (`ref.css` и файлы схем). **Исключение — чисто-компонентная геометрия без sys-дома** (ширина колонки раскладки, unitless `line-height`, `grid-column: 1 / -1` и т.п.): допустима как дефолт **приватной** линии токена (`--_<block>-*`), переопределяемый через публичную (`--hb-<block>-*`). Так делает и Gravity: семантику гонит через токены, компонентные константы держит локально.
5. **Публичные `--hb-<block>-*` — внешний override API.** Их ставит только потребитель снаружи — на контейнере (`.my-slot { --hb-button-height: 52px; }`) или инлайном (`style="--hb-button-height:52px"`). Блок их сам не присваивает, только читает с фолбэком в приватную. Приватные `--_<block>-*` — деталь реализации, не часть публичного API, снаружи не трогаются.
6. **Состояние/модификатор меняет _оформление_ только через приватные токены, но может задавать невизуальные/поведенческие свойства прямо на корне блока:** `cursor`, `pointer-events`, `user-select`, `appearance`, а также `outline`/`outline-offset` для focus-ring (их _значения_ идут из токенов). Это единственное исключение из п. 3 — оно про поведение, не про цвет/размер.

Что это даёт: модификатор пишется без знания внутренностей блока; внешний override публичной линии переживает любой модификатор; тему/схему можно подменить целиком на уровне sys.

## 3. Именование классов (БЭМ)

Классический БЭМ с префиксом библиотеки `hb-` у имени блока.

> **Префикс `hb-` (осознанный выбор).** Каждое имя блока начинается с `hb-`: `.hb-button`, `.hb-text`, `.hb-link`. Это неймспейс библиотеки-источника — стабильный и одинаковый во всех проектах-потребителях, в обоих режимах дистрибуции (зависимость и vendoring). Он снимает конфликты с глобальными именами вроде `.button`/`.text` в чужой разметке и делает блоки библиотеки узнаваемыми в коде потребителя. Префикс — часть имени блока, поэтому в элементах и модификаторах он не повторяется: `.hb-button__icon`, `.hb-button_size_m` (не `.hb-button__hb-icon`). Имена CSS-переменных живут в своём неймспейсе `--hb-*` и от префикса классов не зависят.

- **Блок:** `.hb-button`, `.hb-text`, `.hb-table`.
- **Элемент:** `.hb-button__icon`, `.hb-table__cell` — двойное подчёркивание.
- **Модификатор-значение:** `.hb-button_size_m`, `.hb-text_typography_display-l` — форма `_<property>_<value>`. Для **взаимоисключающих** значений одной оси (есть соседи: `size_s/m/l`, `view_normal/action`, `overflow_ellipsis/fade`).
- **Модификатор-флаг (булев):** `.hb-link_underline`, `.hb-link_visitable` — форма `_<flag>`. Для **независимых** статических on/off-осей, у которых нет оси значений (нельзя осмысленно подобрать соседей). Флаги свободно комбинируются (`class="hb-link hb-link_underline hb-link_visitable"`).

Как выбрать форму: есть осмысленные взаимоисключающие соседи (`_none`, `_fade`, …) → `_<property>_<value>`. Тумблер «включить/нет» без альтернатив (как `visitable`) → `_<flag>`. **Рантайм-состояния** (`disabled`, `checked`, `open`, `loading`, `invalid`) — это НЕ модификаторы, они приходят атрибутами (§4), даже если выглядят как булевы.

**Применение модификатора — всегда чейнингом со своим блоком/элементом:**

```html
<button class="hb-button hb-button_size_m hb-button_variant_ghost">…</button>
<span class="hb-button__icon hb-button__icon_position_right">…</span>
```

```css
.hb-button {
  --_button-height: var(--hb-size-control-height-l);
  height: var(--hb-button-height, var(--_button-height));
}
.hb-button.hb-button_size_m {
  --_button-height: var(--hb-size-control-height-m); /* модификатор → приватная линия */
}
.hb-button__icon.hb-button__icon_position_right {
  order: 1;
}
```

Чейнинг (`.hb-button.hb-button_size_m`, а не голый `.hb-button_size_m`) обязателен: он повышает специфичность модификатора над базой и привязывает модификатор к своему блоку.

### 3.1 Соответствие с Figma

Имена токенов в Figma — slash-separated (`color/text/primary`, `typography/headline-l/size`). В CSS slash → dash: `--hb-color-text-primary`, `--hb-typography-headline-l-size`. Это контракт — имена не должны расходиться, иначе ломается экспорт Figma Variables и Code Connect. Если в Figma встречается имя вроде `Basic/White 48`, эмодзи или служебные символы — токен ещё не готов к экспорту, переименовать на стороне Figma до использования.

### 3.2 Паттерн имени переменной

```
--hb-<category|block>-<part?>-<property>[-<state|variant>]
```

- kebab-case во всём имени;
- `<state>` (`hover`, `focus`, `active`, `disabled`, `selected`, `loading`) и `<variant>` (`danger`, `positive`, `warning`, `info`) — в конце через дефис; имена состояний совпадают с CSS-псевдоклассами (`.hb-button:hover { background: var(--hb-button-background-hover) }` читается без перевода);
- `<part>` (`thumb`, `box`, `label`, `addon`) — между именем блока и property.

Примеры: `--hb-color-text-primary` · `--hb-typography-headline-l-size` · `--hb-button-background-hover` · `--hb-switch-thumb-background`.

### 3.3 Специфичность и cascade policy

Для переносимой CSS-библиотеки специфичность — часть контракта, иначе переопределения у потребителя ведут себя непредсказуемо.

- **Базовый селектор — один класс:** `.hb-button`, `.hb-button__icon`.
- **Модификатор — чейнинг двух классов:** `.hb-button.hb-button_size_m`.
- **Состояние — класс + псевдокласс/атрибут:** `.hb-button:disabled`, `.hb-button[data-loading]`.
- Не используем `id`, теги перед классами, `!important`, глубокие потомковые селекторы и чейнинг более двух классов без необходимости.
- **`:where()`/`:is()` на основных классах не используем** — они обнуляют/усложняют специфичность; допустимы только внутри reset-селекторов самого блока.
- **`@layer`:** ядро не оборачивает себя в `@layer`, чтобы не навязывать cascade policy. Потребитель волен импортировать библиотеку в свой слой (`@import 'index.css' layer(vendor)`) — это его решение, не библиотеки.
- **`box-sizing`:** блок/элемент, которому важны размеры, сам ставит `box-sizing: border-box`. Глобального reset библиотека не поставляет — не зависим от стилей проекта-потребителя.

## 4. Состояния и безголовые библиотеки

Блок различает две природы:

- **Статические оси** (размер, вид, цвет) — БЭМ-модификаторы `_<property>_<value>`. Их ставит автор разметки, в рантайме они не меняются.
- **Динамические состояния** (`open`, `checked`, `disabled`, `loading`, `selected`, `expanded`) приходят **атрибутами** — нативными или от headless-либы. Блок таргетит их селекторами атрибутов и псевдоклассов, а не классами-модификаторами.

Приоритет источников состояния (от частного к общему):

1. Нативные псевдоклассы — `:disabled`, `:checked`, `:focus-visible`, `:hover`, `:active`.
2. ARIA — `[aria-disabled="true"]`, `[aria-checked="true"]`, `[aria-expanded="true"]`, `[aria-selected="true"]`.
3. **`data-*` атрибуты headless-либ.** Единого стандарта нет: Radix ставит `data-state` / `data-disabled`, Headless UI — свои `data-*`, кто-то — только ARIA. Поэтому конкретный набор поддерживаемых атрибутов **фиксируется на уровне блока, а не глобально**, и блок его документирует. Примеры: `button` — `[data-disabled]`, `[data-loading]`; disclosure — `[data-state="open"]`; tab — `[aria-selected="true"]` / `[data-state="active"]`.

**Overlay-блоки** (tooltip/popover/modal/sheet/toast) следуют той же модели: открытость и сторона приходят атрибутами — нативный `[open]` у `<dialog>`/`<details>`, `[data-state="open|closed"]` у headless-либ, `[data-side="top|right|bottom|left"]` для стрелок и направленных анимаций. Конкретный набор фиксируется per-block и документируется в шапке блока. Позиционирование, порталы, стекинг (z-index) и фокус-трап — поведение потребителя; CSS только оформляет состояния.

**`loading` — это library/application state, а не нативное состояние HTML.** CSS его только стилизует. Доступность обеспечивает потребитель: на время загрузки он ставит `aria-busy="true"`, а если действие в это время недоступно — `disabled` / `aria-disabled="true"`. Библиотека не обещает решить a11y состояния одним классом.

Селектор состояния, как и модификатор, переопределяет **оформление только через приватные токены** (невизуальные свойства на корне — по §2.6):

```css
.hb-button {
  --_button-background: var(--hb-color-base-brand);
  --_button-focus-ring-width: var(--hb-focus-ring-width);
  --_button-focus-ring-color: var(--hb-color-line-focus);
  --_button-focus-ring-offset: var(--hb-focus-ring-offset);

  background: var(--hb-button-background, var(--_button-background));
}

/* native */
.hb-button:disabled,
/* aria fallback for non-button elements */
.hb-button[aria-disabled="true"],
/* headless lib (set of attrs is fixed per block) */
.hb-button[data-disabled] {
  --_button-background: var(--hb-color-base-generic-accent-disabled);
  cursor: not-allowed; /* non-visual prop on root — allowed by §2.6 */
}

.hb-button:focus-visible {
  outline: var(--hb-button-focus-ring-width, var(--_button-focus-ring-width)) solid
    var(--hb-button-focus-ring-color, var(--_button-focus-ring-color));
  outline-offset: var(--hb-button-focus-ring-offset, var(--_button-focus-ring-offset));
}
```

Так один блок одинаково работает на нативном `<button>`, на `<a role="button">` и поверх Radix/Headless UI — меняется лишь источник атрибута, не CSS.

## 5. Цвет (light + dark)

Цвет — **отдельный слой**, не часть темы. Геометрия/типографика/анимации обычно одни на проект, а цветовых схем несколько.

Структура:

- `--hb-ref-palette-*` — палитра (блоками не используется);
- `--hb-color-*` — sys-цвета (semantic), их используют блоки через component tokens.

Две схемы с первого дня (Selecta переключает тёмную тему — сайдбар тоже темнеет). Значения берём из тем Gravity: light из `styles/themes/light`, dark из `styles/themes/dark` (см. §11). Дефолтная схема (`light`) объявляется в `:root`, переключение — атрибутом `[data-color-scheme]` на корне документа (без JS-провайдера, совместимо с SSR). Опционально — авто-подхват системной темы через `@media (prefers-color-scheme)`.

```css
:root,
[data-color-scheme='light'] {
  --hb-color-base-background: #ffffff;
  --hb-color-text-primary: #1a1a1a;
}
[data-color-scheme='dark'] {
  --hb-color-base-background: #0e0e10;
  --hb-color-text-primary: #f5f5f5;
}
```

### 5.1 Роли sys-цветов

Блок берёт токен по роли, а не по визуальному значению. Имена ролей — **verbatim из Gravity** (§11): категории `text` / `base` (фон и поверхности) / `line` (границы) / `sfx` (эффекты). Ниже ключевые роли; полный инвентарь — в `styles/themes/*` Gravity, тащим подмножество под нужды экрана.

| Категория       | Паттерн имени            | Ключевые роли                                                                                                                       |
| --------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Текст           | `--hb-color-text-<role>` | `primary`, `secondary`, `hint`, `brand`, `brand-contrast`, `link`, `link-hover`, `info`, `positive`, `warning`, `danger`, `utility` |
| Фон/поверхности | `--hb-color-base-<role>` | `background`, `generic`, `generic-hover`, `generic-accent-disabled`, `brand`, `brand-hover`, `float`, `selection`, `simple-hover`   |
| Границы         | `--hb-color-line-<role>` | `generic`, `generic-hover`, `focus`, `brand`, `info`, `positive`, `warning`, `danger`                                               |
| Эффекты         | `--hb-color-sfx-<role>`  | `shadow`, `shadow-heavy`, `shadow-light`, `veil`, `fade`                                                                            |

**Текст поверх цветной поверхности.** Не подбираем вручную — берём готовую контрастную роль Gravity: `text-brand-contrast` (на brand), `text-light-primary` / `text-dark-primary`, `text-inverted-*`. Контраст обеспечен на уровне токенов донора.

Новые роли не изобретаем: если нужной нет среди уже использованных — берём её из Gravity. Своя роль появляется только если донор реально не покрывает случай.

## 6. Файловая структура

Без сборки, поэтому структура плоская и предсказуемая. Один блок — одна папка с одним `.css`.

```
tokens/
  README.md            # foundation token docs
  ref.css              # --hb-ref-*
  color.css            # --hb-color-* : :root/light + [data-color-scheme=dark]
  typography.css       # --hb-typography-*
  radius.css
  spacing.css          # --hb-spacing-* (секции) + --hb-gap-* (внутри блоков)
  motion.css           # --hb-duration-*, --hb-ease-*
  size.css             # --hb-size-*
  focus.css            # --hb-focus-ring-*
blocks/
  text/
    text.css
    README.md
  button/
    button.css
    README.md
index.css              # @import всех tokens + blocks — entry для демо и дев
demo/
  index.html           # generated navigation по витрине
  text.html            # generated from blocks/text/README.md
  button.html          # generated from blocks/button/README.md
.project/
  SPEC.md              # этот файл
```

- **`index.css`** — единственная точка, где `@import` собирает всё вместе. **Порядок импортов — часть публичного контракта: сначала `tokens/*`, затем `blocks/*/*.css`.** Потребитель может подключить `index.css` целиком либо импортировать нужные `blocks/<name>/<name>.css`, но обязан до этого подключить нужные `tokens/*`.
- **Файл блока намеренно не импортирует ни токены, ни другие блоки.** Зависимость от токенов разрешается порядком подключения, а не `@import` внутри блока — иначе появятся скрытые зависимости и дубли токенов в бандле потребителя.
- **`tokens/` подключаются первыми** — до блоков, иначе `var(--hb-*)` в блоках резолвится в пусто.
- **`tokens/README.md` — source of truth для foundation-слоя**: импортный порядок, назначение token-файлов, scheme model, правила добавления токенов. Отдельные README на каждый token-файл не нужны: токены потребляются как единый слой, а не как независимые компоненты.
- **README блока — source of truth** для назначения, API, анатомии, модификаторов, состояний, публичных токенов, лимитов и примеров. Файл живёт рядом с CSS: `blocks/<name>/README.md`. Язык README и примеров — английский.
- **Демо — generated чистый HTML** в `demo/`, подключает `index.css` и общие стили витрины. `demo/<name>.html` собирается из fenced `html demo` примеров в `blocks/<name>/README.md`; руками редактируется README, а не generated demo. Витрина обязана быть синхронной с реальным составом `index.css` и README блока.
- **CSS-комментарии — короткие и английские.** В начале CSS-файла допускается JSDoc-style metadata block: для блоков `@block`, `@summary`, `@host`, `@modifiers`, `@states`, `@tokens`, `@docs`; для токенов `@foundation`, `@summary`, `@tokens`, `@docs`; для entrypoint `@entry`, `@summary`, `@imports`, `@docs`. Внутри CSS оставляем только точечные пояснения к неочевидным решениям; история порта, отложенные варианты и usage-примеры живут в README.

## 7. Чеклист нового блока

1. **Определить публичный API:** какие переменные нужны для модификаторов и состояний (размеры, цвета, фоны, границы, тени, типографика, padding, gap).
2. **Объявить все эти переменные в корневом селекторе** блока с дефолтами из sys (`var(--hb-color-*)`, `var(--hb-typography-*)`, `var(--hb-radius-*)` …).
3. **Внутри элементов** (`.block__elem`) использовать только `var(--hb-<block>-*)`.
4. **Ноль магических значений** (px, hex, ms). Не хватает в sys — сначала добавить в sys.
5. **Статические оси** — модификаторы `.block.block_mod_val`, переопределяют только component tokens.
6. **Динамические состояния** — селекторы атрибутов/псевдоклассов (§4), тоже только переопределяют component tokens.
7. **Box-sizing:** блок/элемент, которому важны размеры, сам ставит `box-sizing: border-box`. Глобального reset библиотека не поставляет.
8. **Доступность (для интерактивных блоков):** семантический тег по умолчанию; стили `:focus-visible`; анимации респектят `prefers-reduced-motion` — **реализовано централизованно**: `tokens/motion.css` гасит `--hb-duration-*` в `@media (prefers-reduced-motion: reduce)`, блоку достаточно гнать длительности через эти токены (свой `@media`-guard не нужен). **Тач-таргет `≥ 44px`** — требование **touch-таргетных экранов** (мобильные/сенсор): на них через `min-block-size`/`min-inline-size` (не через padding). На десктопе размер задаёт шкала контролов (`--hb-size-control-*`, может быть меньше 44px); под тач берётся размер `l`/`xl` либо высота переопределяется через публичный токен. К не-интерактивным блокам (`text`, `icon`, `table__cell`) тач-таргет не применяется.
9. **README** в `blocks/<block>/README.md` со всеми вариантами/размерами/состояниями, публичными токенами, лимитами и fenced `html demo` примерами.
10. **Демка** в `demo/<block>.html` генерируется из README; блок добавлен в `index.css` и навигацию витрины.
11. **CSS-комментарии:** JSDoc-style шапка + лаконичные английские комментарии только там, где код не объясняет себя сам.
12. **Деградация:** базовый `.block` без модификаторов даёт осмысленный вид на голом HTML.

## 8. Анти-паттерны

- Жёсткие значения в селекторах блока (`padding: 12px`, `color: #fff`).
- Обращение блока к sys-переменным напрямую в не-корневом селекторе — только через component tokens.
- Модификатор/состояние, пишущий в **публичную** линию `--hb-<block>-*` вместо приватной `--_<block>-*` — ломает внешний override.
- Обращение к приватным `--_<block>-*` снаружи блока — это деталь реализации, override идёт через публичную линию.
- Модификатор/состояние, добавляющий селекторы на внутренние элементы вместо переопределения переменных.
- Дублирование значения sys-токена в блоке (копипаст значения вместо `var(...)`).
- Классы, завязанные на структуру DOM, не отражённую в API блока.
- Голый модификатор `.hb-button_size_m` без чейнинга со своим блоком/элементом.
- Состояние, выраженное БЭМ-модификатором (`.hb-button_state_disabled`) вместо нативного/aria/`data-state` (§4).
- Препроцессорный синтаксис (`@include`, `$var`, `@custom-media`) — ломает «без сборки».
- Блок, импортирующий другой блок, или зависящий от порядка подключения блоков.
- Рассинхрон витрины (`demo/*.html`) с реальным составом `index.css`.

Пример **плохого** подхода — [yandex-ui Textinput_view_default.css](https://github.com/bem/yandex-ui/blob/master/src/Textinput/_view/Textinput_view_default.css): модификатор знает про внутреннюю структуру, копипастит селекторы, ломается при рефакторинге.

## 9. Пилотные блоки

Контракт проверяется на реальном потребителе — сайдбаре Selecta (`ThemeControls.vue`, панель форм Vue 3). Не на абстрактной витрине. Если по контракту + исходникам пилотов понятно, как сделать следующий блок, и блок реально встал в сайдбар без переписывания — контракт рабочий.

Порядок продиктован тем, что сайдбару нужно, а не абстракцией:

1. **`text`** (не-интерактивный, смоук-тест контракта). Самый дешёвый блок без состояний — проверяет механику токен → блок → варианты/цвета. Типографика — **из Gravity** (донор, см. §11): шкала `body-1/2/3`, `header-1/2`, `subheader-1/2/3`, `display-1..4`, `caption-1/2`, `code-*`. `viby` и MD3 как источники отпадают — донор один. В Selecta закрывает заголовки групп и подписи.
2. **`button`** (интерактивный, первая реальная победа). Схлопывает экспорт-кнопки Selecta (`.download-button`, `.copy-link-button`, `.export-json-button`, …) в один блок. Проверяет состояния через `:disabled`/`[aria-*]`/`[data-*]`, `:focus-visible`, размеры, варианты.
3. **`field`** (главная дедупликация). Паттерн `label + контрол + actions + error`, повторяющийся в каждой `.control-row` сайдбара. Проверяет блок-обёртку поверх нативных контролов (`input`/`select`/`range`/`color`/`checkbox`), `aria-invalid`, состояния ошибки/варнинга. Хром самих контролов — **отдельные блоки по типу** (`text-input`/`textarea`/`select`/`checkbox`/`radio`/`range`/`color`, как у Gravity — разные компоненты), консистентные через общий слой токенов; не один блок `control`.

Потребление в Selecta: чистый CSS-ядро + тонкие Vue-обёртки, живущие **в Selecta**, эмитящие классы. Ядро на Vue не завязано.

После пилотов — ревизия контракта, затем расширение из словаря `pale-blocks` (`link`, `container`/`stack`, `image`, `embed`, `table`), но **только под нужды следующего реального экрана**, а не пакетом.

## 10. Версионирование публичного API

Публичный API библиотеки — это:

- имена классов (блоки, элементы, модификаторы);
- **публичные** CSS custom properties `--hb-*` (sys-токены + публичная линия component tokens, §2.5);
- структура ожидаемых атрибутов состояний (§4).

Любое переименование или удаление любого из них — **breaking change**. Добавление новых классов / токенов / вариантов — нет.

**Приватные `--_<block>-*` — НЕ часть публичного API.** Их можно переименовывать и реструктурировать свободно: снаружи на них никто не ссылается (§2.5). Это и есть выгода двухлинейной модели — внутренности блока остаются деталью реализации.

## 11. Донор: Gravity UI

Единый источник значений и структуры — [Gravity UI / uikit](https://github.com/gravity-ui/uikit) (MIT). Причина: его CSS-архитектура совпадает с нашим контрактом (двухлинейные CSS-переменные как API, БЭМ, модификаторы только через переменные), у него готовы light/dark-темы и полная шкала типографики. Мы не воспроизводим Gravity целиком — **берём подмножество под нужды конкретного экрана** и расширяем по мере появления следующих. «Тащить всё» = Gravity канонический источник, а не мандат переписать весь Gravity в CSS.

Берём: значения токенов, структуру блоков, light+dark. Дропаем: React, SCSS, `eventBroker`, `forwardRef`, `configure`, `layer-manager`, high-contrast-темы, i18n, Code Connect.

### Рецепт порта компонента из Gravity

1. **Файлы.** `Component.tsx` + `Component.scss` → один `blocks/<name>/<name>.css`. `.tsx` дроп.
2. **Префиксы токенов, двухлинейность сохраняется.** Публичная `--g-<block>-<prop>` → `--hb-<block>-<prop>`; приватная `--_--<prop>` → `--_<block>-<prop>`. Форму `var(--g-x, var(--_--y))` НЕ разворачиваем — просто переименовываем обе линии (§1.3).
3. **БЭМ.** Одиночные модификаторы Gravity `&_view_action` → чейнинг `.hb-button.hb-button_view_action`; `&__icon` → `.hb-button__icon`; `$ns`/`$block` выкинуть.
4. **Состояния → атрибуты (§4).** Классы Gravity `&_disabled`/`&_loading`/`&_selected` → `:disabled` / `[data-disabled]` / `[data-loading]` / `[aria-*]`. (`selected` — по семантике: `[aria-pressed]`/`[aria-selected]`/`[data-selected]`.)
5. **SCSS → плоский CSS.** Инлайнить миксины (`button-reset`, `pin` — радиус на `::before/::after`, `loading`-шиммер); `@use variables` → наши sys-токены; CSS Nesting раскрыть в плоские селекторы (§0).
6. **Роли цвета — verbatim, чистое переименование префикса.** `--g-color-<cat>-<role>` → `--hb-color-<cat>-<role>` (категории `text`/`base`/`line`/`sfx`, §5.1). Никакого маппинга. Тащим только роли, которые реально использует портируемый компонент.
7. **Типографика.** `--g-text-body-1-*` → `--hb-typography-body-1-*` (шкала Gravity, §1.2).
8. **Темы.** Light-значения из `styles/themes/light`, dark — из `styles/themes/dark` → в `tokens/color.css` под `:root`/`[data-color-scheme="dark"]` (§5).
